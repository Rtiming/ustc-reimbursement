# 规范维护与批次规划

本页是[规范体系](../skills/ustc-reimbursement/references/standards-system.md)的工具合同。真实规则、人员、经费和材料留在私有资料；代码只维护结构及算法。工具只做规范登记和离线规划，`system_write`与`finance_write_authorized`始终为`false`，不会生成假财务单或提交报销。

已确认的`summary.contact_location`支持`abstract`与`system_remarks`。后者将原文件夹名（含必要拆单后缀）保留在`summary`，问题联系人单独生成`remarks`供系统备注填写，PDF按该摘要命名。选择位置必须来自当前适用规则；不把摘要复制到转卡附言。`finance.return_location`作为必办要求返回，须核对当前系统枚举后填写，不由离线规划宣称已保存。

## 助手固定操作顺序

新用户尚无规范库时先调用`standards_init(library_root, profile_id, title, mode="student_activity", execute=false)`；mode也可为research_purchase或travel。实际创建加execute=true，只能写授权资料根内的全新目录，不能覆盖已有规范库。生成common与专项空模板后再按下列顺序登记来源和规则；初始化不等于规则确认。

已有库新增专项使用`standards_add_profile(library_root, profile_id, title, parent_ids, execute=false)`。预览冻结before_registry_sha256；执行提供同值expected_registry_sha256。只追加空模式及registry条目，不覆盖旧专项或确认规则；未登记父模式、重复ID、路径冲突、历史目录和旧SHA均拒绝。审计保留registry-before、profile-intent和committed回执。

1. 用`capabilities(intent="rules")`或MCP的`reimbursement_capabilities`找到入口。读取`standards_read(library_root, profile_id)`；`library_root`必须在本机已登记的材料根内，专项从`registry.json`定位，不根据姓名自动选择。
2. 新增要求先辨明是本案决定、长期专项还是材料事实。用`standards_change(library_root, profile_id, change, execute=false)`预览；真实保存再给同一`change`、预览的`before_sha256`作为`expected_sha256`及`execute=true`。这只是私有规范修改，不能拿来授权财务写入。
3. 用`standards_select(library_root, profile_id, context, as_of)`核对适用规则。`context`包含真实`case_id`、`selected_profile_ids`、`selection_basis`和业务范围。日期是要判断规则有效性的业务日期，不是文件下载时间。
4. 依据原件、已有OCR和人工核对结果建立下述归一化对象，再调用`batch_plan(data, export_root=None)`。MCP名称均加`reimbursement_`前缀，参数不变。`export_root`仅用于核对计划文件会不会越界/重名；不创建文件夹或PDF。
5. 先读返回的`needed_inputs`和`next_action`，再逐单看四类就绪度。只补真正缺失的字段；有问题的单据保持`blocked`，其他单据的材料、票数和结构照常展示。需要当前财务身份/经费时沿既有正式财务读取入口核对，不能把历史工号和卡号提示写成已验证。

统一JSON请求由`assistant.py call --input 请求.json`执行。低层CLI是受控离线适配器，不替代统一财务工具。

## 规范记录、版本和冲突

现有`schema_version:1`专项模板及空`rules`兼容读取。每个`rule_id`在当前登记中唯一，修改时沿用ID并提升三段`revision`。`add`新增、`revise`修订、`retire`停用；没有删除历史或任意字段写入动作。

来源以`source_id`登记，`kind`注明`user_instruction`等真实来源类型，`location`指向原文/消息/材料页。用户口述不是老师原文；没有原件时不伪造SHA。已有来源不可静默改写，材料更新另建来源编号。

下面是传给`standards_change`中`change`参数的完整合成例子。原专项须已存在；如来源还没登记，可随本次变更用`sources`增补。

```json
{
  "action": "add",
  "actor": "user",
  "at": "2026-10-22",
  "reason": "登记合成示例中的整理要求",
  "source_refs": ["demo-user-message"],
  "sources": [
    {"source_id": "demo-user-message", "kind": "user_instruction", "location": "合成示例消息", "date": "2026-10-22"}
  ],
  "rule": {
    "rule_id": "summary.contact",
    "revision": "1.0.0",
    "statement": "明白纸底部的问题联系人写入摘要",
    "kind": "user_workflow",
    "status": "confirmed",
    "scope": {"institution": "合成学校"},
    "effect": {"action": "required", "target": "summary.contact_location", "value": "abstract"},
    "source_refs": ["demo-user-message"],
    "confirmation": {"by": "user", "at": "2026-10-22", "source_refs": ["demo-user-message"]},
    "valid_from": null,
    "valid_until": null,
    "supersedes": [],
    "exception_to": []
  }
}
```

`scope`支持`institution`、`organization`、`responsible_person`、`business`、`case_id`、`expense_type`、`funding_code`以及`included_business`/`excluded_business`。普通条件是精确文本或文本数组；业务包含/排除必须是数组。确实全局适用才写`{"all":true}`。`null`代表适用性未知，不能当作匹配；未命中的明确范围只跳过。

`effect.action`为`required/recommended/excluded/ordering/default`之一，`target`是明确事项，`value`是原规则值。它用于比较及展示，不是可执行代码。`proposed/disputed/superseded/retired`规则不会生效；历史样本、待核提取不能直接标成已确认执行依据。对同一事项冲突时不选“最新”或“最严”。

修订完整传回新`rule`，且`supersedes`须明确原`rule_id`、原`revision`、`reason`、`source_refs`；有权本案例外同样使用`exception_to`并限定本案`scope`。只在例外本身范围命中后才覆盖旧项。循环替代、自替代、未解释冲突都会阻塞。已停用规则仍保留，恢复要新版本及明确依据。

模式可通过`extends`组合同库已登记的父模式，最多16层、64项。组合时规则ID转为`profile_id/rule_id`并保留原ID；本地source_refs同样限定所属模式。跨模式的relation添加`profile_id`指明被替代规则所在模式。选择输出增加`profile_sources`（各文件revision/path/sha256）与`composition_order`；单模式旧接口保持原结果结构。旧inherits不自动执行。父模式缺失、循环、范围未知或规则冲突均保留问题，不从同名文件补猜。

执行时在资料根的`.standards-history/<事务ID>/`保存不可变的`before.json`、`after.json`、`intent.json`和成功后`committed.json`，再以原子替换更新规范正本。预览不写文件。旧SHA不符、已有写锁、路径逃逸、链接/重解析点都拒绝修改；遗留写锁要核对该事务，不自动删除重试。历史快照不能通过规范维护入口改写。

## 归一化输入：先对应费用，再规划单据

顶层`schema`固定为`ustc-reimbursement-batch-input-v1`，必须给`case_id`。`policy`必须引用已经确认的本案规则。当前实现的是每单最多50张、最少单数且尽量均衡、同范围已提供金额取小、底部联系人写入摘要；其他规则不能假装支持。

| 字段 | 必须表达的事实 |
|---|---|
| `documents[]` | 一份明白纸及其对应电子材料组；可有多张照片/多页，不是一图一单 |
| `document_id` | 该材料组稳定ID，同批不可重复 |
| `folder_name` / `folder_source_ref` | 电子材料原文件夹名及来源，用作原始摘要；不得用助手概括替换 |
| `clarification.business_date` | `{value,status,source_refs}`，`value`为已核对明白纸上的完整`YYYY-MM-DD` |
| `clarification.responsible_person` / `form_filler` | 明白纸的挂单负责人/填单人原字段分别保留：`{name,phone?,status,source_refs}`；优先级由已确认policy决定 |
| `clarification.contact` | 兼容既有明确指定联系人；新规则优先从上面原字段选择，输出的`selected_contact.basis`保留选择依据 |
| `invoices[]` | `{invoice_id,invoice_number,face_amount,status,source_refs}`；保持逐票原票面，不修改原件 |
| `expenses[]` | 每笔真实费用的稳定`expense_id`、`scope_id`、确认状态、来源及选用`invoice_ids`；不能把一个文件夹机械当一笔不可拆费用 |
| `amount_evidence[]` | 可选已提供的`invoice/list/request`金额证据；每条有`amount,scope_id,status,source_refs` |
| `payments[]` | 每笔费用真实收款分配：`payee_id,name,mode,amount,status,source_refs`；收款身份是本案登记ID，不凭姓名自动推定工号 |
| `native_expense_allocations[]` | 少报时必须有已确认的`native_expense_id,amount,status,source_refs`，说明申请金额落在哪项原生费用；非少报时可省略 |
| `export_sequences[]` | 每张报销单明确文件序号，正整数或保留前导零的数字串；工具不生成未知业务序号 |
| `case_context` | 本案证明人、最终经费批准人、完整经费等；当前原生核对不足只阻塞`finance_readiness` |

所有金额用十进制元字符串（如`"8.01"`），最多两位小数。工具复用现有精确金额校验，不用浮点、四舍五入或`null→0`。`status:"confirmed"`和`source_refs`表示调用方已经完成所需事实核对；工具不会因OCR有字就替你确认，也不会验证引用资料的全部原件字节。单独的`amount_status`若存在也必须为`confirmed`；`amount_origin`可用`document_content/verified_extract`，文件名金额`filename`只作候选，不能进入取小计算。文字层拆乱的小写数字、未复核OCR金额保持未确认。

明确的文件名实报另用`amount_origin:"filename_explicit_claim"`，仅适用于唯一完整发票范围的`amount_evidence.kind:"request"`，不得作为`invoices[].face_amount`或清单来源。该记录须含`invoice_id/invoice_number`，并与对应发票共同保留相同的`source_archive/source_archive_sha256/source_chain`；成员链必须为本活动目录内的精确原ZIP成员，文件名唯一明确“物资 10元 实报8元”且票面、申请额均一致，申请不得超过票面。两者`source_refs`须共同引用唯一原件绝对路径、SHA及`&page=页码`；申请记录还须以`claim_basis_ref`引用已有逐票依据（`绝对路径.json#sha256=SHA/rows/行号`），并将该引用列入`source_refs`。这里核对的是已确认来源声明的闭合，不新增文件读取或代替实际字节SHA核验。原票面保留，申请额显示为`candidate_claim_total`；该来源目前始终保留`FILENAME_CLAIM_NATIVE_REVIEW_REQUIRED`，即使填入`native_expense_id`也不升级为执行就绪，仍需原生映射、保存和独立持久回读。

本专项明确采用`policy.contact_priority:["responsible_person","form_filler"]`时，优先挂单负责人；只有该原字段已确认空白，才选填单人。空白写`{name:null,blank:true,status:"confirmed",source_refs:[...]}`；未识别、未提供或单独`name:null`不表示空白。`contact_fields`保留原两项，`selected_contact.basis`记录选中字段、优先级及前序空白依据。有姓名没有电话也可以规划，不能编号码。

同票多份文件使用一个发票实体的多个`source_refs`；相同完整票号且金额/状态一致的多个载体合并计数，冲突则阻塞。重开票等旧版记录保留在`invoices`，以费用的`excluded_invoice_ids`明确排除；旧版不能同时选用。费用ID不能因票版增加而重复。没有明确归属或排除的票不会被丢掉。

同票涉及多笔费用时，每笔费用须有`invoice_allocations:[{invoice_id,amount,source_refs}]`，全部费用对该票的分配合计必须等于原票面；没有这种证据则金额留空。相关费用同单，票只计一次。`keep_together`是可选的明确不可拆组编号；工具不会为突破50张而拆散它。多张票属于同一真实费用时，也作为不可拆组；不要为了通过校验虚构逐票费用。

金额取小只针对同一费用、同一比较范围的已提供且已确认依据：逐票原金额（或明确共票分配）为发票基准，再比较`amount_evidence`。缺省的清单/申请金额表示未提供，不强制补齐三类；已列出却未识别、未确认、范围不一致则阻塞。取小一次后按真实费用所在单相加，不在拆后再次按总额扣减，也不按张数比例摊钱。

单据整体才有一个较小总额、无法落实到真实费用/收款人时，保留该证据及金额待办，不编造每票分摊来凑齐输入。可以先提供已确认的费用关联及票数结构，金额保持`blocked`。少报后原生费用和支付合计都必须等于申请额；票面字段始终不变。

角色由`policy.required_roles`和`policy.prohibited_roles`决定，支持`witness/final_funding_approver/pre_reviewer/acceptance_person`。同一个姓名不自动填入其他角色。真实姓名、工号、经费卡不在公共代码中。已有当前原生核对才给`native_verified:true`及`native_source_refs`；经费须有`complete:true`与完整`code`。历史提示仅可用于寻找候选。

## 从一个合成新案走到计划

将下面完整请求保存到临时目录的`request.json`。它仅含合成材料；`case_context`故意为空，预期金额、结构和导出命名为`ready`，总体和`finance_readiness`为`blocked`，不会访问财务。示例不是实际票据、收款账户或办理授权。

```json
{
  "method": "batch_plan",
  "params": {
    "data": {
      "schema": "ustc-reimbursement-batch-input-v1",
      "case_id": "synthetic-new-case",
      "policy": {
        "status": "confirmed",
        "source_refs": ["synthetic-user-rule"],
        "max_invoices_per_form": 50,
        "split_strategy": "minimal_balanced",
        "amount_strategy": "minimum_comparable",
        "contact_in_summary": true,
        "contact_priority": ["responsible_person", "form_filler"],
        "required_roles": ["witness", "final_funding_approver"],
        "prohibited_roles": ["pre_reviewer"]
      },
      "case_context": {},
      "documents": [
        {
          "document_id": "paper-demo-1",
          "folder_name": "合成活动耗材",
          "folder_source_ref": "synthetic.zip!/合成活动耗材/",
          "clarification": {
            "business_date": {"value": "2026-09-02", "status": "confirmed", "source_refs": ["synthetic-paper:p1"]},
            "responsible_person": {"name": "合成联系人", "status": "confirmed", "source_refs": ["synthetic-paper:p2"]},
            "form_filler": {"name": "合成填单人", "status": "confirmed", "source_refs": ["synthetic-paper:p2"]}
          },
          "invoices": [
            {"invoice_id": "I1", "invoice_number": "99000000000000000001", "face_amount": "10.00", "status": "confirmed", "source_refs": ["synthetic-invoice:p1"]}
          ],
          "expenses": [
            {
              "expense_id": "E1",
              "scope_id": "demo-materials",
              "status": "confirmed",
              "source_refs": ["synthetic-paper:p1", "synthetic-invoice:p1"],
              "invoice_ids": ["I1"],
              "amount_evidence": [
                {"kind": "list", "amount": "12.00", "scope_id": "demo-materials", "status": "confirmed", "source_refs": ["synthetic-list:p1"]}
              ],
              "payments": [
                {"payee_id": "P1", "name": "合成收款人", "mode": "bank_transfer", "amount": "10.00", "status": "confirmed", "source_refs": ["synthetic-paper:p1"]}
              ]
            }
          ],
          "export_sequences": ["001"]
        }
      ]
    }
  }
}
```

从工具仓运行`python assistant.py call --input 请求文件绝对路径`；Mac可用`python3`。不需旧案、浏览器或任何私有账号即可得到结果。统一入口对本例的业务`blocked`可返回非零退出码及`ok:false`，应读JSON的待补字段，不把它当连接故障重试财务动作。直接离线CLI则将上例`params.data`保存为`input.json`，执行`python tools/reimbursement_batch_plan.py --input 输入文件绝对路径`；增加`--output 全新计划JSON绝对路径`才写派生计划，已有同名计划拒绝覆盖。两平台CLI都输出UTF-8 JSON。

本例应得到一个单据、1张票、票面与申请额均为`10.00`、摘要`合成活动耗材；报销有问题请联系合成联系人`、相对导出路径`2026-09-02/001_合成活动耗材；报销有问题请联系合成联系人.pdf`。没有发明缺省申请金额、电话号码、工号、卡号或审批状态。

若把清单改成`8.00`，会列出支付不一致及少报原生费用分配待办；真实依据未取得前不改付款为8元来“通过”。若日期只识别出`09-02`，日期与导出路径留空，要求核对年份。若后续有51张独立费用发票，最少拆2单、26/25张，摘要分别加`（一）`和`（二）`，金额仍从各自真实费用相加。

## 返回值与接续

| 返回字段 | 正确读法 |
|---|---|
| `status` | 总体`ready/blocked`，`ready`仅表示离线输入和计划就绪 |
| `structure_readiness` | 票据身份、唯一费用归属和最少张数拆分是否明确 |
| `amount_readiness` | 可比金额、逐费用申请额、实际收款与少报原生映射是否闭合 |
| `export_readiness` | 原摘要、底部联系人、真实业务日期、明确序号和目标名是否齐备 |
| `finance_readiness` | 本案真实角色及经费的当前原生核对是否充分；不表示获批 |
| `issues` / `needed_inputs` | 每项给`field/code/detail`；保留来源并补指定字段，不把整批移回未开始 |
| `next_action` | 明确`method/action/fields/instruction`；补齐后再调该固定方法，不自拼财务操作 |
| `candidate_claim_total` | 仍有支付/结构待核时的候选算术值，不可作为可执行申请额 |
| `claim_amount` | 完成相应结构和金额校验后的离线金额；受阻留空 |
| `forms[].export` | PDF导出计划，包含日期、序号、安全文件名及路径；`pdf_generated:false` |

文件名清理Windows/Mac共同非法字符、保留原摘要独立字段，日期文件夹仅用已确认业务日期。输入与本批计划的重名、目标已有同名文件均阻塞且禁止覆盖。没有`export_root`只能比较本批内部重名，不能宣称目标目录已核对。

拆分先用最少单数`ceil(唯一选用票数/50)`；独立单票尽量均分，明确不可拆组用确定性装箱和有界回溯。不可拆组超过50、最少单数装不下或搜索预算耗尽均列明待决策，不偷偷多开单或超过50。`balance_optimal_proven`只在全部原子组均为单票时为真；有不可拆组不宣称全局最均衡。

## 实现与验证

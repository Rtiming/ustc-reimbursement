# 底层业务接口

统一JSON方法`business`、MCP `reimbursement_business`复用同一参数、任务和artifact/SHA合同。学校请求经当前浏览器会话发出，固定`WF_YBX`、固定端点和本人账号；不导出Cookie，不接任意URL、SQL、JS、窗口号或过程名。脚本和输入在任务目录冻结，未知结果保留原任务。

## 迁移项目与验收指标（2026-10-28）

项目目标：将现有报销业务逐项迁入已核实的学校HTTP接口，同时保留案件参数、金额及身份校验、授权、原任务恢复和交付追溯。范围包含下方职责表全部财务域；本地材料、OCR、规则和总账沿原owner保留。最终交付为同一CLI/JSON/MCP入口、模块实现、合成测试、干净分发包及对应真实回执。仅禁用旧点击路径不算迁移完成。

完成状态分别登记：`待适配`、`实现及离线验证通过`、`真实只读验证通过`、`真实授权写入及独立回读通过`。每个动作按本身性质选择验收层级；只读、预览、发现定义及模拟响应不能使写动作升级为已实测。无法进行真实写入验收的动作明确保留该缺项，不新建、批准或修改真实报销单来凑测试样本。

### 本轮接续路线（2026-10-28会话修复后）

按现有owner继续补说明/预审、上传与票据/建单、完整支付与劳务、提交/审批及明细/列表导出，不绕过原pending和本案授权。先核官方固定定义、上下文与原生计算，预检冻结原字段及声明变更，写入后新发完整HTTP回读；未取得所需定义或现场样本的动作保留具体未验项，不能只解除旧路径禁用。真实测试不修改已预约待投递单据，也不新建测试报销单；沿现有获准案件和流程状态接续。

清单保持本人全部单据、全部36列、总数/分页/重复及账号校验。当前88单改前5次独立任务为6.90–15.38秒，中位7.01秒（不足20次，不判P95）。学校查询占约5.1–13.1秒；先比较官方查询及计数路径，再优化实际热点，禁止靠减少覆盖或持久旧快照报提速。诊断的交错有计数/无计数请求耗时相近，四次完整结果SHA一致，不采用取消计数作为提速方案。新源码及本轮证据保存在`.local/native-completion-20261028/`，沿本页更新最终状态。

## 基本信息的写入与恢复

公开入口仍为`stage`；已接入的阶段为`basic/funding/expenses/payments/notes/pre-review`，各自适用范围见下文。默认`execute=false`输出本地计划；执行须给当前`tab_id`，账号来自本案`expected_userid`或已绑定执行会话。摘要、手机/电话、改签标志、退单地点、备注及教师工号/姓名均从本案`form.basic`读取，不接受调用者临时传字段、URL或过程。已有流程或非草稿不得保存。旧`finance_cli basic`和`run_case --execute`停止执行控件脚本。

```json
{"method":"enqueue","params":{"case_id":"本案标识","operation":"stage","parameters":{"stage":"basic","tab_id":"当前数字标签"},"request_id":"稳定阶段请求号","execute":true}}
```

`finance_native_stage.py`持有写入生命周期，`finance_basic_api.js`持有基本信息规则，`finance_native_protocol.js`持有原生命令编码。执行顺序：完整HTTP预检→冻结输入/定义/31个原字段及变更计划→创建原`pending_write`→重新核对同号同金额草稿与原计划→一次保存。无变更时不调用保存过程，但仍要求独立回读。所有证据归原job目录，输入和预检有SHA，不另建案件状态库。

保存后用`business(action="bill-read",domain="basic")`发起新的只读任务，再通过原`record_result(kind="ack-write",outcome="saved")`引用该任务的`output.json` artifact。登记同时验证：原保存脚本已结束；回读在结束之后派发；账号、单号和金额一致；全部原字段及声明变更后的值逐项相等；本案form和冻结证据SHA未变。只有成功登记后才解除pending并将basic加入`operator_verified_stages`。正式进程退出或学校返回pass不等于保存验收。

超时、连接中断、响应不明确、服务端judge/error以及字段不符均不重发。原脚本未结束时先`read_system(mode="recover")`读取原marker；随后仅独立读取。`not_applied`只接受同案同号的“派发前拒绝”明确回执及原字段完整回读，不能凭数据看似未变解除一个未知保存。换request_id也不能绕过同案pending。批次`fill_stage/basic`和原pending恢复复用此合同；旧批次其他阶段尚未因此迁移成功。

本项当前为“实现及离线验证通过”；真实预检曾通过，真实保存及速度指标尚未验收。2026-10-28旧页404曾被误判为学校后端不可用；本机新入口重新认证后，同一YBX接口已恢复，详见下方会话恢复记录。本轮未派发财务保存，未创建测试报销单。

### 2026-10-31 原单短信验证交接

`business definitions domain=submission` 通过固定 `activation_ifsend.action` 读取服务器实际验证状态；配置启用验证不等于本次尚未验证。该读取不发送短信、不提交本人同意。

`access action=applicant-verification-open` 接收原单 `plan`、当前 `tab_id` 和授权 JSON 的 `{path,sha256}`，须 `execute=true`。只对金额、摘要、当前账号和申请人 508 节点均一致的已有单据开放。授权文件须逐单列出 `case_id/serial/current_amount`，明确同意、保留短信验证、不新建单据。真实服务器已验证时只返回 `already_verified`；未验证时在无其他编辑任务的页面打开学校原生验证界面。

业务读取采用固定 HTTP；人工验证界面采用经定义与处理函数 SHA 校验的学校原生 renderer。此交接不点击同意、不发送短信、不读写验证码。用户在学校窗口确认验证码后，学校自己的回调可能继续当前原单，后续必须先独立回读节点，不得直接重复申请人同意。其他编辑页面、其他单号验证窗和未确认的旧写任务均保留。

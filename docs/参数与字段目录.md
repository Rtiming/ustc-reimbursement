# 参数与字段目录

[中文](参数与字段目录.md) | [English](en/interfaces.md)

普通助手从[统一操作规程](助手操作规程.md)及`cases → overview`开始。安装后的JSON入口为`sh tools/reimbursement.sh call --input 请求文件绝对路径`，Windows用`tools\reimbursement.cmd`；它们复用本项目运行时。本页保留底层动作/字段参考，日常无需拼历史脚本。

## 使用者需要给什么

先提供活动/业务简述、时间地点、人员名单和角色、逐张发票、实际支付及拟报金额、收款人、经费卡、审批安排、附加材料。金额是字符串，最多两位小数；人员号和单号也是字符串，保留前导0。未知身份、用途、银行卡及事实不能猜。

`case.json`保存事实、决定和材料，form与invoices文件保存填表参数及一票一文件的原件路径、SHA和票号候选，具体文件名以本案operator.json为准；new_case建立的新案使用form.json和invoices.json。下一案用`reimburse.py init`或MCP new_case创建空参数，不复制旧案事实或全局替换旧脚本中的单号。接口update_case按最新revision合并业务输入，金额等结构由check核对；见[助手接口](助手接口使用.md)。

## 填表参数

| 参数 | 内容与必填条件 | 实际填入能力 |
|---|---|---|
| case_id、serial、amount | 案件名、当前系统单号、核定总额 | 每次写入核对域名、系统、单号和金额 |
| basic.teacher_id/name | 已确认教师工号与姓名 | 工号原生change解析，核对本案已确认姓名 |
| basic.fields.t-abst | 摘要，按本案已确认规则绑定原始材料名称 | 原生基本信息输入框；联系人在摘要或备注的位置由所选规则决定 |
| t-req_mobile、t-req_tele | 联系方式 | 原生字段；不采用历史默认电话 |
| t-is_have_changefee | 是否含项目负责人费用，枚举Y/N | 只填原生可选枚举 |
| t-td_point | 退单地点枚举 | 按当前原生候选和本案要求选择 |
| t-cl_abst | 备注/资金分配及已确认的问题联系说明 | 普通文本，与摘要和转卡附言分别配置 |
| funding[].code/name/amount | 每张经费卡及金额 | 原生列表按代码选，单/多项目模式，检查配置外已选项目 |
| expense_allocations[] | project、subject、budget、amount | 每个预算叶节点显式给值，0元也要列；校验科目、项目和总额 |
| payments[].mode | bank_transfer / corporate_card | 当前仅这两种金额填写完成实测 |
| payments[].person_id/name/amount/remark | 工号、姓名、金额、可选转卡附言 | 转卡原生候选唯一匹配、银行联动后填金额；不在配置收集完整银行卡；只有显式remark才写附言，空字符串清空，省略则保留原生值；不继承摘要、备注或旧payment_remark |
| corporate_card.transaction | date、merchant、card_suffix、search_period，可选search_amount | 查询必须给正确金额；查询值去除小数尾随0，不保留无效的尾随0；按人员/日期/商户/卡尾号/金额选唯一记录 |
| pre_review[].id/name | 已确认预审人，按顺序，最多4 | 原生人员输入/保存；按本案确认的顺序；系统窗口支持“工号/姓名”格式 |
| funding[].department_approver | 单位审批人id/name | 匹配原生xmSelect候选，写sdata并等上下文回写，不能把项目负责人当院级审批人 |
| explanations.general | 简短整体说明 | 系统“上传其他附件”中的文本说明 |
| explanations.source_file/source_text_sha256 | 定稿正文相对配置的路径、正文SHA | CLI自动核对文件与内嵌general一致；不改写用户定稿 |
| explanations.card_notes[] | 每人金额和text | 分人分段保存在同一补充说明字段；本单未出现独立专用字段，不能谎称存在两个独立字段 |
| contract.exists | false是已确认无合同；有合同另走真实关联合同流程 | 无合同使用原生“否”选项，不填虚构编号，不以无合同躲避采购规定 |
| review.ordinary_promise_authorized | 普通承诺是否已获授权 | 原生承诺确认；最终本人同意须独立授权，验证码由本人填写 |
| review.workflow_started | 此单是否已生成流程 | 已生成时阻止再次执行承诺/整套review |
| delivery | 打印模式、原件与跨单引用 | 材料计划与交付检查；不凭全电发票自动选择委托打印 |

当前多条公务卡、汇款、质保金、内部转账均未完成参数写入实测。汇款/质保金的原生字段已发现，新增适配器后才能启用正数支付，不能混入本案的转卡数组。

已创建但尚未填完整的草稿，可用受控`finance_cli.py navigate/status`读取身份或打开原生栏目，仍须本案真实单号、日常模式及正金额；不为查看候选填写占位证明人、经费或分摊。所有实际填写、保存动作继续要求完整配置及三组合计闭合。

转卡附言按原生上限校验：最多25字符单位，汉字按2单位计（最多12个汉字）。填写前校验显式附言，保存前再核对当前原生值。原生校验拒绝保存时返回`not_saved:true`；保存后须等支付窗口退出并出现同号预览才返回成功，等待超时仍标记`unknown_verify_before_retry`，不能重放原写请求。

若仅出现已知的“转卡附言最大长度大于设定长度25字”错误，可用固定恢复动作解除该校验提示并走原生“返回”，不保存、不处理其他提示：

```text
python3 tools/finance_cli.py dismiss-payment-remark-error --case 本案配置JSON绝对路径 --tab-id 当前标签ID --output 全新回执JSON绝对路径
```

该动作核对真实单号和金额，精确匹配唯一校验提示，点其“确认”后只点支付页“返回”，等待同号预览。恢复不修改案件或承认原写入结果；之后独立回读实际付款字段，再按原pending登记`needs_correction`。修正时用新意图显式提供合适的`remark`或空字符串，不能重发原保存请求。

## 报销项金额窗口与逐票减报

`finance_expense_amount.py`适配日常草稿的原生“报销项详情”窗口。可见金额格提示“可点击修改报销金额，修改的金额不能大于发票金额”，参数含费用分组与科目；底层打开入口含存储过程，因此`open`不是只读动作。来源检查、原生打开、独立回读、逐票保存及返回分别留证。支持完整390行及原生保存后返回41预览的闭环；276后续窗口不自动处理。

MCP为`reimbursement_expense_amount`；JSON准确入口是`enqueue`、`operation:"expense_amount"`，没有同名JSON直调方法。固定参数为`group`、`subject`、`expected_userid`、`tab_id`；真实`serial`从本案已绑定配置读取。以下为合成示例：

```json
{
  "method": "enqueue",
  "params": {
    "case_id": "synthetic_amount",
    "operation": "expense_amount",
    "parameters": {"action": "inspect", "group": "合成费用", "subject": "30201", "expected_userid": "SYNTH001", "tab_id": "99"},
    "request_id": "synthetic-amount-inspect-01",
    "execute": false
  }
}
```

| 动作 | 来源与执行条件 | 回执及下一步 |
|---|---|---|
| `inspect` | 初次读取本案可见金额入口、41原生定义和已加载282窗口；打开后给原`open/return`任务的`job_id/artifact_id` | 只读固定窗口的实际字段、输入值、按钮定义及`xtype`；不猜字段。`capture_complete:false`保持受阻 |
| `open` | `source_job_id/source_artifact_id`引用同案独立`inspect`；默认`execute:false`只给计划，`true`才真实打开 | 复核同号同账号、唯一可见分组/科目金额格和完整原生定义，只点击一次；建立`expense_amount:open` pending，`amount_save_requested:false` |
| `return` | 来源为打开后的独立`inspect`，需有原打开请求标记；默认只给计划，`execute:true`才返回 | 只有已检查且当前未变的原生“返回”纯关闭定义可执行；含业务过程、保存或未知处理器明确拒绝，字段改变也不丢弃。建立自己的pending |
| `recover` | 原`open/return`任务`job_id/artifact_id`与保留的同标签marker | 仅读取原marker和当前282窗口，绝不再次点击入口或返回 |
| `save` | `source_job_id/source_artifact_id`指向同案已打开窗口的完整独立检查；`claims_path`为授权材料范围中的JSON数组 | 逐项列窗口全部票的`invoice_guid/invoice_number/face_amount/claim_amount/amount_origin/source_refs`；来源须绑定路径、SHA及页码。先重算冻结准备，再检查所有原字段、金额、分支和保存定义，只改金额格并点击一次原生保存。不支持任意字段或跨票借额 |

`open/return`后另做`inspect`，再以其独立回执调用`record_result(kind="ack-write",outcome="staged")`：打开须同号同账号、本组`xtype`和实际可见282字段；返回须窗口退出、同号预览及原分组金额一致。此专用ack拒绝`saved/not_applied/needs_correction`，不登记财务金额已保存。未知、窗口尚未就绪或定义不明时保留原pending，继续原任务恢复与独立检查，不换请求号重放。

`save`后使用新的完整原生预览独立回读；`ack-write(saved)`核对原保存请求绑定、同号账号、无错误弹框、完整预览和原分组新金额，仅登记分组保存结果。随后必须从新金额预览重新打开同组，完整检查390行并用`verify_saved_rows`逐票核对GUID、完整票号、票面、ord和实报额；相同总额下任意两票挪动金额仍拒绝。逐票持久回读前，不把准备文件、保存请求或分组总额当作逐票完成。

新减报单若须先按票面生成原生可调整草稿，case决策及`material_context.reduction_target`须明确原票面、最终申请额和阶段；暂存金额不作为最终申请或支付依据。最终金额保存并独立回读后再更新正式form、预算、收款和批次计划。未完成时保留办理中，不进入正式完成计数或提交。

`tksbcodecnt`可在保存过程返回后产生；保存前两处原生上下文均未定义时，只有已核验SHA的原生`btnClickFunc`（先call_proc、成功后routeActs）才允许延后判断，不把空值当0，也不赋值或替换分支。已有值为276分支、来源不完整或驱动变化仍受阻。保存后若出现276或其他窗口，保留原保存意图并独立检查，不重存。

多组费用逐组冻结、单次保存和持久回读；不放宽选票原票面校验，不编造逐票扣减。正式批次登记`material_context.native_reduction_receipts[]`的`save_job_id/save_artifact_id/rows_job_id/rows_artifact_id`；工具从同案注册SHA回执重算准备、核对重开行时间、原票GUID及票面、全部少报金额和计划`native_expense_allocations`。`native_expense_id`取实际390行的`t-tk_guid`。票据一览继续核对原票面总额，单据/预算/收款核对申请额。手填verified标记不能使少报案通过批次核验。

## 校验和停止条件

执行前`validate_config.py`核对支付、经费、分摊三组均等于总额，检查每张卡分摊、人员号、重复收款和未接通的支付模式。JS还核对当前单号、可见窗口、原生候选、银行卡回填和保存前支付闭合。无候选、多候选、预算不足、原件SHA变化、已有金额冲突、未认证或占用发票均停在受影响步骤。

查询没有结果先核对格式与条件。例如虚构金额10.00的查询值可规范为10，正式报销金额仍保留两位小数；空查询不能直接当成没有公务卡记录。未知事实集中问，普通承诺和无关紧要的已授权选项不重复问。

`explanations.record_only=true`表示仅存用户文本，此时工具不自动改现有单内说明。`material_context.profiles`选择student_activity/research_purchase/travel；条件及`materials[].role/status`定义所需材料，运行audit_materials给出缺件。材料已存在、已匹配、已上传、原件已交分别记录。

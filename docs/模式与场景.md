# 使用场景与专项模式

工具只有一套。组织、老师、项目和经费的差异通过数据表示，不为每位老师复制代码或整份技能。

## 按实际任务选择一组工具

| 用户要做什么 | 起点 | 输入与产物 | 什么时候完成 |
|---|---|---|---|
| 整理刚收到的电子包 | materials / material_intake | 原包、来源、资料根→原件清单、SHA、材料工作区 | 原件已归档，缺项可追到具体材料 |
| 建立组织或项目口径 | standards_init/read/change/select | 制度、审核意见、确认来源→有效规则及冲突 | 来源、范围和确认状态明确；不是获得审批 |
| 核对金额并规划分单 | prepare_batch_file | 已核归一化材料、专项、业务日期→离线计划 | 结构、金额、导出、财务就绪度分别有结论 |
| 填写或恢复原单 | cases → overview → workflow | 明确案件、账号、原单和授权→逐步回执 | 本阶段保存经独立回读；未知结果保留原任务 |
| 取得系统PDF与清单 | export-system / export-list | 同案原生页面、命名映射→原文件归档 | 明细与列表分别有文件回执 |

## 模式包含什么

材料场景使用现有三个标识：学生活动`student_activity`、科研采购`research_purchase`、差旅`travel`。场景只是检索与材料分类入口，不能自动决定费用范围、限额、经费或申请人身份。

规则模式使用私人规范库中登记的`profile_id`。可以让`project_alpha`通过`extends:["common","student_rules"]`引用共用与学生活动规则，再只写项目差异。父模式必须在同一个registry中明确登记；不自动查找同名老师、联网下载规则或跨目录加载代码。

| 层次 | 放什么 | 不放什么 |
|---|---|---|
| 通用工具 | 数据结构、原件保护、任务恢复、固定接口 | 某个人的电话、经费、收款账户、默认批准 |
| 单位/场景共用规范 | 已核的本单位制度、材料要求、流程约定 | 其他学校或历史案件自动继承的资格 |
| 组织/项目专项 | 与共用规范相比真实存在的差异及来源 | 另一份完整工具或无来源的覆盖规则 |
| 本次案件 | 人员、票据、金额、经费、授权、例外与进度 | 自动推广成所有项目规则的临时安排 |
| 设备配置 | 本机路径、适配器、登录人及凭据引用 | 作为共享附件发送的密码、Cookie或会话数据库 |

## 组合、冲突和版本

新增的`extends`会真正组合已登记规则，按父模式在前的顺序返回来源链及各文件SHA。旧模板的`inherits`只作历史说明，不能悄悄启用旧库中不存在的父模式。迁移时明确登记父模式，再将引用改成`extends`。

组合规则采用`模式ID/规则ID`定位，保留`origin_profile_id/origin_rule_id`。两个模式都叫`limit`不会相互覆盖。相同事项的要求不同则阻塞；只有有来源、精确版本且范围匹配的`exception_to/supersedes`才能消去旧项。跨模式引用额外写`profile_id`，例如引用`common`中的`limit@1.0.0`。规则层级并不赋予下级推翻学校制度的权限。

初始化只生成空的`common`与一个专项，状态为收集中。空模式不等于没有材料要求；没有已确认规划规则时，prepare_batch_file会列出缺项。材料检查器使用的`data/material_rules.json`是另一份运行配置，本包初始明确为未配置；不得将空配置当作材料齐全。

在新项目中复用规则时保存新版本及来源，不改历史快照。不要把本次已报或已付状态写进规则，也不要把选择规则的结果当作财务授权。
